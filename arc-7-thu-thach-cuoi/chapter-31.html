Phần 1: Nỗi Sợ Của Developer (Fear of Breaking Things) (5 phút)

Người kể chuyện

Lâm Tuấn bước vào Sàn Đấu Thử Nghiệm. Không khí ở đây lạnh lẽo và đầy sát khí. Tại đây, anh gặp Sư Đệ Minh - người có biệt danh là "Kẻ Hủy Diệt Bug". Toàn thân hắn ta đeo đầy những lá bùa màu xanh lá cây (Green Bar).

Sư Đệ Minh

Chào sư huynh. Huynh có bao giờ sửa một chức năng cũ, nhưng lại sợ làm hỏng những chức năng khác không?

Lâm Tuấn

Có chứ! Cảm giác đó gọi là "Depression Driven Development". Mỗi lần sửa code là tim đập chân run.

Sư Đệ Minh

Để trị bệnh sợ hãi đó, chúng ta dùng Automated Testing (Thử Nghiệm Tự Động). Thay vì nhờ con người test (vừa chậm vừa hay quên), ta viết code để test code của chính mình. Và công cụ trấn phái chính là JUnit 5.

Phần 2: Cấu Trúc Trận Pháp (@Test) (10 phút)

Sư Đệ Minh

Một bài test đơn giản gồm 3 phần: Arrange (Chuẩn bị), Act (Hành động), Assert (Khẳng định). Huynh chỉ cần tạo một method và dán bùa @Test lên trên. Ví dụ: Test hàm cộng 1 + 1.

Lâm Tuấn

`@Test` `void testAddition()` { Calculator calc = new Calculator(); // Arrange int result = calc.add(1, 1); // Act // Assert? Làm sao để nói nó phải bằng 2? }

Sư Đệ Minh

Dùng class `Assertions`. `Assertions.assertEquals(2, result, "1 + 1 phải bằng 2 chứ đồ ngốc!");` Nếu kết quả đúng, huynh sẽ thấy một thanh màu xanh (Green Bar) tuyệt đẹp. Nếu sai (Red Bar), huynh sẽ biết ngay mình vừa phá hỏng cái gì.

Phần 3: Vòng Đời Thử Nghiệm (Lifecycle) (7 phút)

Lâm Tuấn

Nhưng nếu đệ tử có 100 cái test, cái nào cũng phải `new Calculator()` thì mỏi tay lắm.

Sư Đệ Minh

Hãy dùng các Lifecycle Annotations. @BeforeEach: Chạy trước mỗi test case (Dùng để khởi tạo mới object). @AfterEach: Chạy sau mỗi test case (Dùng để dọn dẹp). @BeforeAll: Chạy đúng 1 lần duy nhất khi bắt đầu class test (Dùng để kết nối Database giả). Phải là static method. @AfterAll: Chạy đúng 1 lần duy nhất khi kết thúc tất cả.

Lâm Tuấn

Thật tiện lợi! Vậy là môi trường test luôn sạch sẽ, không bị nhiễm bẩn từ test này sang test kia.

Phần 4: Tổng Kết (5 phút)

Người kể chuyện

Lâm Tuấn viết thử vài cái test đơn giản. Cảm giác nhìn thanh Green Bar hiện lên thật gây nghiện (Dopamine). Nó mang lại sự tự tin tuyệt đối. Anh biết code của mình chạy đúng mà không cần phải bật cả server lên để bấm click click.

Sư Đệ Minh

Đây mới chỉ là khởi đầu. Huynh đang test những class đơn giản (POJO). Nhưng trong Spring, các class phụ thuộc lẫn nhau chằng chịt. Làm sao huynh test `UserService` khi nó cần `UserRepository`, mà `UserRepository` lại cần Database thật? Ngày mai, ta sẽ dạy huynh tuyệt kỹ Mocking (Huyễn Thuật Giả Lập).

📚 Thuật Ngữ Chương Này

  • JUnit 5 Framework testing tiêu chuẩn cho Java. Phiên bản 5 gồm Jupiter, Vintage và Platform.
  • @Test Annotation đánh dấu một method là một test case.
  • Assertions Class chứa các hàm static (assertEquals, assertTrue, assertThrows) để kiểm tra kết quả thực tế so với mong đợi.
  • @BeforeEach / @AfterEach Lifecycle hooks chạy trước và sau mỗi test method, đảm bảo tính cô lập (Isolation) của test.

💼 Câu Hỏi Phỏng Vấn

  1. Tại sao phải viết Unit Test? (Đảm bảo chất lượng, dám refactor, document code, phát hiện bug sớm).
  2. Sự khác nhau giữa @BeforeAll và @BeforeEach? (@BeforeAll chạy 1 lần/class và phải static. @BeforeEach chạy n lần/n test methods).
  3. AssertThrows dùng để làm gì? (Kiểm tra xem code có ném ra Exception mong muốn hay không).
  4. TDD (Test Driven Development) là gì? (Viết Test trước -> Test đỏ -> Viết Code -> Test xanh -> Refactor).

🔮 Tiếp Theo

Thế giới thực rất phức tạp. UserService không thể chạy nếu thiếu UserRepository. Nhưng kết nối Database thật thì quá chậm và rủi ro. Lâm Tuấn cần một "hình nhân thế mạng" để đóng giả UserRepository.
