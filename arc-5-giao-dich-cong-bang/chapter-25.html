Phần 2: Triển Khai Transaction (10 phút)

Lâm Tuấn

Đầu tiên, đệ tử viết hàm log: `@Transactional(propagation = Propagation.REQUIRES_NEW)` `public void logTransaction(String message) { ... }` Để đảm bảo Log luôn được ghi lại bất chấp kết quả.

Lâm Tuấn

Tiếp theo là hàm chính `transfer`: `@Transactional(rollbackFor = Exception.class, timeout = 5)` `public void transfer(Long fromId, Long toId, BigDecimal amount) {` ` try {` ` // Logic trừ tiền, cộng tiền` ` auditService.logTransaction("Success");` ` } catch (Exception e) {` ` auditService.logTransaction("Failed: " + e.getMessage());` ` throw e; // Ném lại để kích hoạt Rollback` ` }` `}`

Đường Chủ Transaction

Khá lắm. Nhưng logic trừ tiền của ngươi thế nào? Có kiểm tra số dư không? Và quan trọng nhất, ngươi có dùng Pessimistic Locking không?

Phần 3: Đối Mặt Deadlock (12 phút)

Lâm Tuấn

Khoá bi quan (Pessimistic Lock)? Ý Đường Chủ là `SELECT ... FOR UPDATE`?

Đường Chủ Transaction

Đúng. Nếu ngươi chỉ `findById`, rồi java check `balance > amout`, rồi `save`. Thì khi 2 thread chạy cùng lúc, chúng đều thấy số dư đủ, và đều trừ tiền. Kết quả là số dư bị âm (Lost Update). Ngươi phải dùng: `@Lock(LockModeType.PESSIMISTIC_WRITE)` trong Repository khi lấy thông tin người gửi.

Đường Chủ Transaction

Nhưng coi chừng Deadlock. Tình huống: A chuyển cho B. B chuyển cho A. Cùng một lúc. Thread 1 khóa A, chờ khóa B. Thread 2 khóa B, chờ khóa A. Cả 2 chờ nhau đến thiên thu. Giải pháp là gì?

Lâm Tuấn

(Suy nghĩ hồi lâu) Đệ tử nhớ rồi! Phải luôn khóa tài nguyên theo một thứ tự nhất định. Ví dụ: Luôn khóa ID nhỏ trước, ID lớn sau. `User first = fromId < toId ? fromUser : toUser;` `User second=fromId < toId ? toUser : fromUser;` Như vậy sẽ không bao giờ bị vòng tròn luẩn quẩn.

Đường Chủ Transaction

Xuất sắc! Ngươi đã ngộ ra chân lý của Concurrency Control.

Phần 4: Tổng Kết Arc 5 (8 phút)

Người kể chuyện

Hệ thống ngân hàng của Lâm Tuấn hoạt động trơn tru. Tiền bạc phân minh, sổ sách rõ ràng. Các đệ tử trong môn phái vô cùng tin tưởng vào uy tín của hệ thống. Lâm Tuấn thở phào nhẹ nhõm. Anh đã vượt qua được một trong những Arc khó nhằn nhất về mặt tư duy logic.

Sư Phụ Cao Nhân

(Vỗ vai Lâm Tuấn) Chúc mừng đệ tử. Nhưng ta thấy dạo này ngươi hay phải viết code lặp đi lặp lại ở nhiều nơi: Code Log, Code đo thời gian chạy, Code check quyền Security... Chúng cứ bám vào code nghiệp vụ (Business Logic) như dây leo ký sinh vậy. Nhìn rất rối mắt.

Lâm Tuấn

Đúng là vậy ạ. Code `transferMoney` của đệ tử tuy an toàn nhưng đầy rẫy code `audit`, code `try-catch`.

Sư Phụ Cao Nhân

Đã đến lúc ngươi cần học về AOP - Aspect Oriented Programming (Lập Trình Hướng Khía Cạnh). Một loại pháp thuật cho phép tàng hình, tách những thứ rườm rà đó ra khỏi code chính. Hãy đến gặp Trưởng Lão AOP ở Arc tiếp theo.

📚 Tổng Kết Arc 5

  • Pessimistic Locking Cơ chế khóa bi quan. Khóa dữ liệu ngay khi đọc (SELECT ... FOR UPDATE) để ngăn người khác sửa. An toàn nhưng chậm.
  • Optimistic Locking Cơ chế khóa lạc quan. Dùng cột version để check khi update. Nếu version lệch -> Ném lỗi. Nhanh hơn nhưng phải xử lý retry.
  • Deadlock (Khóa Chết) Tình huống 2 process chờ nhau giải phóng tài nguyên mãi mãi. Giải quyết bằng thứ tự khóa đồng nhất (Consistent Ordering).
  • Race Condition Lỗi xảy ra khi kết quả phụ thuộc vào thứ tự thực thi không kiểm soát của các thread.

💼 Câu Hỏi Phỏng Vấn Tổng Hợp

  1. Làm thế nào để tránh Deadlock trong Database? (Access resources theo đúng 1 thứ tự, giữ transaction ngắn gọn).
  2. Optimistic vs Pessimistic Locking: Khi nào dùng cái nào? (Optimistic cho hệ thống đọc nhiều ghi ít. Pessimistic cho hệ thống ghi nhiều, xung đột cao như tài chính).
  3. Spring @Transactional có hoạt động với Private Method không? (Không, vì AOP Proxy chỉ chặn được Public Method gọi từ bên ngoài).
  4. Tại sao try-catch trong Transaction lại có thể làm hỏng cơ chế Rollback? (Vì nuốt mất Exception khiến Spring không biết có lỗi. Phải throw lại hoặc setRollbackOnly).
